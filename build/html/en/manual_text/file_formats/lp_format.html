LP File Format Description¶

The LP format, widely used in academia and industry, has the advantage of being more readable than the MPS format. Unlike the column-based format of MPS files, LP files describe problems using row expressions and do not have a fixed writing range or length. However, from the perspectives of processing performance and readability, various solvers have standardized the maximum byte length of each line. The OptVerse solver reads a buffer of 16 kB. It is advised to keep lines shorter than this 16 kB limit, although lines longer than this will still be parsed correctly.

Below, we provide a standard LP file:

\ENCODING-ISO-8859-1

\Problem name:Maximize
Maximize
obj:x1 + 2 x2 + 3 x3 + x4
Subject To
 r1: - x1 + x2 + x3 + 10 x4 <= 20
 r2: x1 - 3 x2 + x3 <= 30
 r3: x2 - 3.5 x4 = 0
Bounds
 0 <= x1 <=40
 2 <= x4 <= 3
Generals
 x4
Binaries
 x3
End

Problem, Maximize, Subject To, Bounds, Generals, Binaries, General Constraints, and End are the indicator words for each section. The ordering of these sections matters and should adhere to the order specified in this document.

Each section indicator word must be written on a separate line and is not case-sensitive. Below, we provide detailed descriptions of each part of the file.

Additionally, a BNF description can be found here.

Comments in LP Format¶

Content following a backslash (\) is considered a comment and will be ignored by the solver without parsing. Similarly, blank lines in the file will also be ignored. For example:

\ENCODING-ISO-8859-1

\Problem name:Maximize

Keywords in LP Format¶

Keywords in LP format can be in one of three forms:

  1. All uppercase (e.g. PROBLEM)

  2. All lowercase (e.g. problem)

  3. First letter capitalized (e.g. Problem)

The minimization (maximization) keyword is an optional first valid field in the format. If omitted, the solver defaults to a minimization problem. The end keyword marks the end of the problem description. Anything after end will not be parsed.

LP Format Sections¶

Before introducing sections, we first introduce two concepts: tokens and expressions. A token is the smallest unit that can be processed at once and cannot be split by inserting any characters, such as spaces or newline characters. We consider numbers, strings, keywords, operators, and relational symbols as tokens. An expression is a group of tokens formed by combining tokens with spaces. We only support using spaces as token separators in token groups. For example, in the expression 10 x1 + x2 + 2000, 10 and 2000 are number tokens, variable names x1 and x2 are string tokens, and tokens are separated by spaces. The expression 10,x1,+,x2,+,2000 is not a token group; it is just a string.

Strings are treated as an alphanumeric string of characters, which may additionally contain special characters. Strings must not begin with any of the following symbols: *, +, < >, =, (, ), ^, :, /, ,, or .. Strings must not begin with a number, nor can they be a keyword.

It is not a variable name because variable names, constraint names, and objective function names need to meet the following criteria: they must be different from each other, their names must not exceed 255 characters in length, they cannot start with numbers or operators +, -, *, ^, and relational symbols <, >, =, and they cannot be keywords. It is not recommended to use the E +number format for variable names, such as E9 or e9, as this will be interpreted as a number. It is recommended to use a combination of characters and numbers, such as var001.

Problem Name Section [Optional]¶

Users may provide a name for their model through this section. If a name is not provided, the solver will assume the name optv for the model name.

Objective Function Section¶

The objective function can start with the maximize or minimize keyword. Its format is:

minimize
-x1 + x2 + -x3 + 0.5 x1 + 100 + x4 + 20

In the above format:

  1. minimize appears alone on one line.

  2. Variables can be directly connected with the minus sign (-), such as x1 and x3.

  3. Variables can appear multiple times, and we aggregate the coefficients, in this example, the coefficient of x1 is -1 + 0.5.

  4. Offsets can appear in the middle or at the end of the expression, such as 100 and 20. Multiple offsets are summed.

In actual usage, the objective function can have a name and can be written over multiple lines, but attention should be paid to some details, such as:

minimize
obj: -x1 + x2 + -x3 + 0.5 x1
+ 100 + x4 + x5 + 1.5 + 2.0
x6

The objective function name needs to be followed by a colon (:) as a separator; when line breaks occur, tokens are the smallest unit. If no objective function name is provided, obj will be inferred as the objective name and a warning will be displayed.

Multiple Objectives¶

The OptVerse solver supports multi-objective problems as well. Multi-objective models must have linear objectives, with no quadratic terms. An empty objective is permitted for multi-objective problems. Each objective in a multi-objective model must have a header that includes the following information:

  1. [Optional] name of objective, with colon to indicate end of name

  2. Priority

  3. Weight (may be signed)

  4. Absolute tolerance

  5. Relative tolerance

The format for these parameters is as follows, with an illustrative example of specifying multiple objectives:

obj1: Priority=2 Weight=1.0 AbsTol=1.0e-6 RelTol=0.0
 x0 + x1 + 2
obj2: Priority=1 Weight=1.0 AbsTol=1.0e-6 RelTol=0.0
 3 x0 + 2 x1 - 3

Quadratic Objectives¶

Objective functions may optionally contain quadratic terms. A quadratic region of the objective is enclosed by brackets [ <quad terms> ] and should be followed by / 2, where the spaces are optional. If / 2 is not provided, this will still be inferred and a warning will be displayed. Division by values other than 2 will result in a syntax error. If a user wishes to avoid this division, they will have to multiply the terms in the file before reading in the .lp file.

There are two ways to express a quadratic term:

  1. x^2, or x ^ 2

  2. x*x, or x * x

either forms are accepted, with the spacing around the * and ^ symbols being optional. Cross-terms are indicated with * whereas diagonals may use either * or ^. A coefficient of 1.0 is inferred if not provided for quadratic terms.

For efficiency, it is best to order your terms such that they are increasing in the lowest index variable, e.g:

minimize
obj: -2.0 x1 +3.0 x2 -1.0 x3 + [ x1^2 + x2^2 + x1 * x2 + x3^2 + x1 * x3 + x2 * x3 ] / 2

should be written as:

minimize
obj: -2.0 x1 +3.0 x2 -1.0 x3 + [ x1^2 + x1 * x2 + x1 * x3 + x2^2 + x2 * x3 + x3^2 ] / 2

Constraints Section¶

The keyword subject to for specifying constraints must also be written on a separate line. Each new constraint must start on a new line. Constraints can optionally provide constraint names, followed by a colon after the constraint name. Constraint names must follow the same rules as variable names. If a constraint name is not provided, one will be inferred as R_# where # is the total number of rows when adding.

Constraints are defined as linear expressions composed of variables, constants, and operators, followed by a relational symbol and a coefficient on the right-hand side. Using one of the following relational symbols can intuitively indicate the meaning of the constraint: >=, <=, or =. For example, here is a named constraint:

subject to:
depts01: -x1 + 0.5 x2 <= 40

However, it is not allowed to have expressions on both sides of the relational symbol, such as:

subject to:
depts02: -x1 + 0.5 x2 <= 40 + x1

And double-sided relational symbols, such as:

subject to:
depts03: 0 <= -x1 + 0.5 x2 <= 40 + x1 <= 40

Quadratic Constraints¶

Just like the objective function expression, constraint expressions can also be written over multiple lines, but consistency is required.

Constraint expressions may also optionally contain quadratic terms. A quadratic region of the constraint is enclosed by brackets [ <quad terms> ]. Unlike objectives, they should not be followed by / 2. There are two ways to express a quadratic term:

  1. x^2, or x ^ 2

  2. x*x, or x * x

either forms are accepted, with the spacing around the * and ^ symbols being optional. Cross-terms are indicated with * whereas diagonals may use either * or ^. A coefficient of 1.0 is inferred if not provided for quadratic terms.

For efficiency, it is best to order your terms such that they are increasing in the lowest index variable, e.g:

subject to:
c1: -2.0 x1 +3.0 x2 -1.0 x3 + [ x1^2 + x2^2 + x1 * x2 + x3^2 + x1 * x3 + x2 * x3 ]

should be written as:

subject to:
c1: -2.0 x1 +3.0 x2 -1.0 x3 + [ x1^2 + x1 * x2 + x1 * x3 + x2^2 + x2 * x3 + x3^2 ]

Indicator Constraints¶

A constraint may be represented as an indicator constraint. An indicator constraint allows conditionally including a constraint in the problem if some binary condition is met. An indicator constraint is formatted starting with an optional name, followed (in order) by a binary variable, equals sign, a value of 0 or 1, an arrow “->”, and finally an unlabelled linear constraint.

For example:

ind0: x = 0 -> y + z <= 20

Bounds Section [Optional]¶

The bounds section is optional. If it exists, it indicates that variable bounds provided need to be used for the variables. Depending on the number of bounds provided, each expression in a line can be divided into single bounds or double bounds. Single bounds can be x >= 10 or x < 10, while double bounds can be 10 <= x <= 15. Neither type of bound allows for multi-line writing. If variable bounds are not provided, the solver’s internal values will be used by default. If a single bound is defined for a variable, the appropriate default bound will be used as the second bound.

There are several guidelines to follow:

  1. Fixed bound expressions are not allowed; that is, they cannot be written as x1 = 20 but should be uniformly written as 20 <= x1 <= 20.

  2. Supports +(-)inf, such as x1 > -inf.

  3. Supports free, such as x1 free.

Generals and Binaries Sections [Optional]¶

The generals and binaries sections in an LP file are used to indicate variables that must have integer values in feasible solutions. These two sections have similar formats, so we introduce them together in one section; in practice, their presence or absence does not affect each other. Variables registered in these two sections will have default bounds defined. For variables registered in the generals section, the default range is \(0\) to \(10^{20}\). For variables registered in the binaries section, the default bounds are \(0\) and \(1\). Variables are registered by listing them in the corresponding section, such as:

Generals
x4 x5 x6 x7
x8 x9

Binaries
x1 x2 x3 x4

As shown, different variables are separated by spaces, and multi-line writing is allowed. Also, variables can be registered in different sections. For example, for variable x4, the final variable type is determined by the smallest feasible range.

Variable designation can appear in any order or multiple times. If a variable is designated more than once, the final assignment will be respected.

SOS Constraints Section [Optional]¶

The sos section allows users to specify an SOS constraint for the model. Each SOS constraint must start on a new line, and must end with a newline. SOS constraints may optionally have a name, followed by a colon after the SOS constraint name. If a constraint name is not provided, one will be inferred as SOS_# where # is the number of SOS constraints. SOS names must be followed by an SOS type signifier (one of S1 or S2) followed by two colons. Finally, a space-separated list of variables and weights are provided for the SOS constraints.

An example SOS section is provided for illustration:

SOS
   sos1: S1::    x : 1.0    y : 2.0
   sos2: S2::   x : 1.0    z : 2.0

General Constraints Section [Optional]¶

Supported General Constraints¶

Constraint

Keyword

Description

And

AND

Resultant variable is non-zero if all supplied variables are non-zero.

Or

OR

Resultant variable is non-zero if any of the supplied variables are non-zero.

Max

MAX

Resultant variable is equal to maximum of supplied values and variables.

Min

MIN

Resultant variable is equal to minimum of supplied values and variables.

The general constraints section allows users to specify general constraints in the model, similarly to the subject to section. Each new general constraint must start on a new line. General constraints can optionally provide names, followed by a colon after the constraint name. Constraint names must follow the same rules as variable names. If a constraint name is not provided, one will be inferred as GC_# where # is the total number of general constraints when adding.

The general constraints in .lp files follow the same general specification. They are started by an optional name delimited by a :. After the constraint name, the user provides a variable name that represents the “resultant” followed by an equals sign. After the equality, the user must provide a general constraint type specifier (e.g. AND, or OR). Finally, the user must supply a comma separated list of variables which specify the constraint behaviour.

Consider the following examples:

General Constraints
    and1: r1 = AND ( x1, x2, x3 )
    and2: r2 = AND ( x3, x1 )
    or1: r3 = OR ( x1, x2, x3 )
    or2: r4 = OR ( x3, x1 )
    max1: r5 = MAX ( x1, x2, 10.0 )
    min1: r6 = MIN ( x1, x2, 10.0 )

Note

At present, our solver only supports LP and QP problems, and does not support nonlinear fields, semi-continuous, or semi-integer types.
